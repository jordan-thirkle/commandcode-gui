Architecture

An Electron + TypeScript desktop app that drives the real Command Code CLI through its documented headless JSON protocol — no fork, no private protocol.

The bridge: spawn the CLI, stream the JSON

Every chat run is a child process: cmd -p --output-format json <prompt>. The app parses newline-delimited JSON frames and renders them natively.

# One run, documented protocol
cmd -p --output-format json "polish the HUD" \
  --model deepseek/deepseek-v4-pro --effort high

# Events stream as NDJSON, one object per line
{"type": "event", "event": {"type": "tool_running", ...}}
{"type": "event", "event": {"type": "text_delta", ...}}
{"type": "result", "subtype": "success", "sessionId": "...", ...}

Unknown event types are ignored, per the protocol's forward-compatibility contract. The GUI renders the stream; it never depends on terminal scraping.

A swap seam for the future

The transport is isolated behind a Bridge interface. Today it spawns the CLI; tomorrow it can import the engine directly without touching the UI.

CliBridge (today)

Spawns cmd -p --output-format json, parses the NDJSON stream into typed events, surfaces exit codes (3 auth, 4 permission, 8 max-turns, 10 credits…).

HarnessBridge (future)

Once the engine's @commandcode/harness is published as a consumable package, the same interface can embed it in-process. The UI never changes.

The Windows cmd.exe fix

On Windows, the CLI and the system shell share a name. This is the kind of detail that breaks apps silently.

Typing cmd on Windows resolves to C:\Windows\System32\cmd.exe — the shell — which shadows the npm-installed Command Code CLI. The app resolves the real CLI executable at runtime:

# Resolution order (resolveCmd.ts)
1. npm global prefix → node_modules/command-code/dist/index.mjs
2. a command-code binary on PATH (skipping cmd.exe)
3. fall back to cmd on non-Windows

Without this, every run would silently drop into an interactive shell instead of executing the agent.

Cost-optimal model routing

The app ships presets that match a proven project convention: spend deep-reasoning tokens where quality is judged, and cheap tokens on bulk work.

PresetModelWhen
Build / runner (default)deepseek/deepseek-v4-proBuilder sessions and the gauntlet runner — long-context reasoning
Quality-criticalgpt-5.6-lunaThe visual critic and architecture decisions
Bulk / mechanicalxiaomi/mimo-v2.5-proRepetitive, cache-heavy loops
Balancedclaude-sonnet-5Everyday mixed work

The GUI never hardcodes a model id in the UI logic — it reads the catalog and offers presets, so new models are just data.

Stack & layout

Electron main

Window lifecycle, the RunManager that owns one CLI child per run, IPC to the renderer, and the session/MCP/skills/agents readers.

React + Vite renderer

The whole GUI: chat feed, session tree, gauntlet board, model picker, status bar. Context-isolated preload; no node integration in the window.

Gauntlet engine

A pure state machine (define → split → build → check → critic → iterate) plus a critic adapter that invokes the project's visual-critic agent on real PNGs.
